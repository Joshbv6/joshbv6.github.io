SECURITY ENGINEERING APPROACH

From Software Engineering to Application Security

I Understand How Software Is Built

Before moving into security, I spent years as the developer on the other side — designing, building, and shipping production applications under real delivery pressure. I know what it feels like to receive a security finding two days before a release. That background means I can integrate security requirements without creating friction, because I understand how software actually gets built, not just how it should be secured.

I Build Security Into the SDLC

Security problems are cheapest to fix before code is written, and most expensive after it ships. My approach is prevention-first: threat modeling at design time, security requirements baked into stories, SAST and SCA running in CI/CD, and secure code review as a normal part of the development loop — not a gate bolted on at the end.

I Turn Vulnerabilities Into Action

A finding without context is noise. I focus on understanding why a vulnerability exists, what it actually puts at risk, and what the most practical fix looks like for that codebase — so developers get actionable guidance, not a report to ignore. From CVE triage to OWASP Top 10 patterns, the goal is always the same: fix it, understand it, prevent the next one.

I Automate Security at Scale

I believe effective security should become part of the engineering process rather than a manual gate at the end. My experience with Jenkins, Semgrep, SonarQube, OWASP Dependency-Check, OWASP ZAP, Docker, and Linux security allows me to automate security checks and move security earlier in the development lifecycle.

Security isn't a feature.
It's an engineering discipline.
